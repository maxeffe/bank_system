# Банковская система

Учебный проект: многоуровневая банковская платформа на чистом Python.
Модели счетов, управление клиентами, система транзакций, безопасность и отчётность.

Задание состоит из 7 этапов. Все готовы.

```
   день 1   типы счетов, наследование, полиморфизм          готово
   день 2   валидация, исключения, инкапсуляция             готово
   день 3   Client, Bank, безопасность, отчёты              готово
   день 4   Transaction, очередь, процессор                 готово
   день 5   AuditLog, RiskAnalyzer, отчёты аудита           готово
   день 6   демонстрация: очередь, отказы, риск, отчёты      готово
   день 7   ReportBuilder: текст, JSON, CSV, графики        готово
```

## Требования

```
   Python 3.12
   loguru 0.7.x      структурные логи
   matplotlib 3.11.x  графики отчётов
   pytest 9.x        только для тестов

```


## Принципы проектирования

```
   инкапсуляция      состояние закрыто; счёт сам держит правила статуса: CLOSED
                     окончательный, закрыть можно только пустой счёт; коллекции
                     наружу - копиями, журнал аудита - глубокими копиями
   наследование      AbstractAccount -> BankAccount -> Savings / Premium / Investment
   полиморфизм       одно правило снятия в BankAccount.withdraw; тип счёта меняет
                     только хуки: _check_withdraw_limit, withdrawal_fee,
                     min_allowed_balance; проверок типа снаружи нет
   абстракция        ABC-контракт счёта; _debit с откатом; таблицы обработчиков
                     по TransactionType и типам счетов вместо if/elif

   SRP               Bank - реестр; вход, аудит, риск, отчёты, аналитика - сервисы;
                     форматы и графики отчётов - в отдельных модулях
   OCP               новый тип счёта или транзакции - одна запись в словаре
   LSP               withdraw наследника только зовёт super(); поведение меняют
                     хуки и своё сообщение INSUFFICIENT_FUNDS_MESSAGE
   ISP               процессор знает у банка только converter, time_provider,
                     get_account, assess_transaction, ensure_can_process,
                     record_outcome
   DIP               часы (time_provider), курсы, журнал аудита, внешний шлюз -
                     внедряются; процессор и отчёты по умолчанию берут часы банка

   доменная модель   Money как Decimal с копейками, статусы - StrEnum, переходы
                     транзакции только методами; владелец счёта записан один раз
                     (account.user_id)
   логирование       loguru, событие = имя + поля: deposit, withdrawal, refund,
                     interest_applied, transaction_queued / completed / rejected
   юнит-тесты        время, курсы и шлюз подставляются без моков; тесты проходят
                     в любое время суток
```

## Архитектура

Зависимости идут только сверху вниз. Счёт не знает про банк, клиент не знает
про счета: владелец записан в самом счёте (`account.user_id`).

```
   enums / exceptions / money          словарь состояний, ошибок и денег
          |
          v
   accounts.py       client.py         один счёт; владелец: ФИО, контакты, пароль
          |               |
          +-------+-------+
                  v
   bank.py                   реестр всех клиентов и счетов, аудит, поиск
          |
          v
   transactions / queue / processor    операции над счетами через банк
          |
          v
   main.py                   сценарий и вывод, без бизнес-логики
```

`Bank` хранит клиентов и счета и владеет жизненным циклом счёта. Всё остальное
вынесено в сервисы, каждый из которых проверяется без банка:

```
   Bank (реестр)
     |
     +-- AuditLog        единое хранилище событий
     |     ^
     |     +-- FraudJournal    подозрительные действия, запрет 00:00-05:00
     |     +-- RiskAnalyzer    пишет оценки и итоги, держит историю клиента
     |     +-- AuditReporter   строит отчёты
     |
     +-- AuthService     проверка пароля, блокировка после 3 попыток
     +-- BankAnalytics   общий баланс и рейтинг клиентов
```

Анализатор риска банк собирает сам — поверх своего журнала, курсов и часов;
снаружи настраиваются только пороги: `Bank(risk_settings={"large_amount": ...})`.

## Счета

```
   AbstractAccount (ABC)          контракт: deposit, withdraw, get_account_info
        |
        +-- BankAccount           обычный счёт + все проверки и property
              |
              +-- SavingsAccount     неснижаемый остаток, месячные проценты
              +-- PremiumAccount     овердрафт, фиксированная комиссия, лимит снятия
              +-- InvestmentAccount  портфель (stocks/bonds/etf), прогноз роста
```

Статус счёта проверяется первым в любой операции — единым методом
`ensure_operational`. `CLOSED` — финальное состояние: обратно в `ACTIVE` или
`FROZEN` счёт не вернётся, а закрыть можно только пустой счёт — это правило
проверяет сам счёт, при создании и при любой смене статуса.

Снятие устроено как шаблон: одно правило в `BankAccount.withdraw`, а тип счёта
меняет только хуки. `withdraw` возвращает, сколько реально ушло со счёта.

```
   withdraw(amount)
      1. ensure_operational          статус
      2. _validate_amount            сумма
      3. _check_withdraw_limit       лимит одного снятия
      4. withdrawal_fee              комиссия
      5. min_allowed_balance         нижняя граница баланса

                        лимит            комиссия     нижняя граница
   BankAccount          нет              0            0
   SavingsAccount       нет              0            min_balance
   PremiumAccount       withdraw_limit   fixed_fee    -overdraft_limit
   InvestmentAccount    нет              0            0
```

## Деньги

Все суммы — `Decimal`, ровно два знака после запятой.

```
   разрешено    int, Decimal
   запрещено    float, bool, Decimal NaN, Decimal Infinity, строки
```

`float` запрещён намеренно: `Decimal + float` бросает `TypeError`, поэтому
дешевле не пускать его на вход, чем ловить взрыв в середине операции.
Округление до копеек — `ROUND_HALF_UP`, кроме пересчёта валют в операциях:

```
   зачисление   вниз    получатель не получает больше заплаченного
   списание     вверх   но не больше запрошенной суммы

   50.00 EUR -> USD:  55.555 -> зачислено 55.55 USD,
                      они стоят 49.995 -> списано 50.00 EUR
```

Доля копейки остаётся у банка, из воздуха деньги не появляются.

## Клиенты и безопасность

```
   возраст            не младше 18
   контакты           только email и phone, оба строки, с проверкой формата
   пароль             pbkdf2-hmac-sha256, случайная соль, 200 000 итераций
   сравнение пароля   hmac.compare_digest, устойчиво к атаке по времени
   вход               3 неверные попытки -> статус BLOCKED
   аудит              оценки, итоги операций и подозрительные действия
                      в AuditLog, опционально в JSONL
   риск               HIGH-риск операции блокируются до списания
   ночь               операции запрещены с 00:00 до 05:00
```

Открытый пароль нигде не хранится. Время в банк передаётся через
`time_provider`, поэтому ночной запрет тестируется без ожидания.

## Транзакции

```
   PENDING (сразу) / SCHEDULED (с датой) --отмена--> CANCELLED
      |
      | срок наступил
      v
   PROCESSING --успех--> COMPLETED
      |
      +------ошибка----> FAILED (+ причина отказа)
```

`Transaction` хранит id, тип, сумму, валюту, комиссию, отправителя, получателя,
статус, причину отказа, число попыток и три отметки времени.

`TransactionQueue` — куча с ключом `(приоритет, порядковый номер)`: HIGH раньше
NORMAL раньше LOW, внутри приоритета — FIFO. Отложенные транзакции пропускаются
до наступления срока и не блокируют очередь. Отмена — ленивое удаление.

`TransactionProcessor` считает комиссию, конвертирует валюту, повторяет попытки
и ведёт журнал ошибок.

```
   комиссия      внутренние операции          0
                 внешний перевод              max(1% от суммы, 50 руб)

   конвертация   курсы банка, все через рубль, нет курса -> CurrencyConversionError

   повторы       деловая ошибка   (заморожен, нет денег)  -> сразу FAILED
                 временная ошибка (внешний шлюз недоступен) -> до 3 попыток

   откат         если вторая половина перевода упала,
                 деньги возвращаются отправителю
```

Статусы обоих счетов проверяются до первого движения денег, поэтому перевод на
замороженный счёт не может списать сумму с отправителя.

## Правила переводов

```
   уход в минус     запрещён, кроме PremiumAccount с овердрафтом
   замороженный
   или закрытый     операции запрещены обеим сторонам
   внешний перевод  облагается комиссией
```

## Аудит и риск

### AuditLog

Одно хранилище событий на весь банк. `FraudJournal` пишет сюда же,
а `journal.actions` собирается обратно из журнала.

```
   record(event, severity, client_id, account_id, now, **details)
        |
        1. проверка, копия, JSON, кодировка utf-8   ошибка -> InvalidOperationError
        2. файл JSONL (если задан file_path)        ошибка -> AuditWriteError
        3. список в памяти                          только если 1 и 2 прошли
        4. loguru с уровнем по severity             INFO / WARNING / CRITICAL

   filter(severity, min_severity, event, client_id, account_id, since, until)
        все условия вместе, наружу только копии записей
```

Сначала файл, потом память — чтобы при сбое записи они не разошлись.
`Decimal` пишется в JSON строкой, чтобы не терять копейки.

События, которые пишет банк:

```
   transaction_assessed    оценка риска, до движения денег
   transaction_completed   операция прошла, с остатками счетов после неё
   transaction_failed      операция упала, с именем ошибки
   fraud_action            неверный пароль, заблокированный клиент, ночь
   account_opened          открыт счёт, с начальным остатком
```

### RiskAnalyzer

```
   правило               условие                                        вес
   ------------------------------------------------------------------------
   large_amount          сумма в RUB > 100 000                            2
   frequent_operations   уже 5+ операций клиента за 5 минут               2
   new_counterparty      перевод на счёт, куда у клиента ещё не было      1
                         завершённого перевода
   night_time            час операции в 00:00-05:00                       1

   сумма весов   0-1 LOW       2-3 MEDIUM        4+ HIGH
                 INFO          WARNING           CRITICAL + блокировка
```

Пороги — аргументы конструктора с этими значениями по умолчанию. Для правил
анализатор держит короткую историю клиента: моменты операций и получателей
завершённых переводов. Журнал нужен для отчётов, решение о блокировке от него
не зависит.

### Блокировка

```
   TransactionProcessor.process(tx)
        |
        1. bank.assess_transaction(tx)       один раз на транзакцию
              |
              +-- HIGH   -> клиент SUSPICIOUS, RiskBlockedError -> FAILED
              +-- MEDIUM -> WARNING в аудит, дальше
              +-- LOW    -> INFO в аудит, дальше
        |
        2. попытки: ночное окно, комиссия, движение денег
        |
        3. bank.record_outcome(tx, error)    completed / failed в аудит
```

Риск проверяется до первого движения денег. Если не записывается оценка,
операция не проходит. Если не записался только итог, очередь идёт дальше,
а в лог уходит `audit_outcome_lost`.

### Отчёты

```
   bank.get_suspicious_operations(client_id=None)   записи WARNING и выше
   bank.get_client_risk_profile(client_id)          операции, худший уровень,
                                                    блокировки, частота правил
   bank.get_client_history(client_id)               свои операции и завершённые
                                                    входящие переводы
   bank.get_transaction_statistics()                исполнено / отклонено, по типам,
                                                    по риску, оборот и комиссии
   bank.get_error_statistics(processor.errors)      ошибки по типам, каждая попытка
   bank.get_clients_ranking()                       клиенты по балансу в RUB
   bank.get_total_balance()                         общий баланс в RUB
```

История строится из итогов операций в аудите: упавший входящий перевод
получателю не показывается, уровень риска виден только у своих операций.
Сумма и валюта в строке истории — это сумма и валюта самой транзакции.

## Отчёты и графики (день 7)

`ReportBuilder` собирает три вида отчётов только из публичного API банка
и отдаёт их в трёх форматах плюс PNG-графики.

```
   builder = ReportBuilder(bank)
        |
        +-- client_report(client_id)   сводка клиента   таблица: история операций
        +-- bank_report()              сводка банка     таблица: все счета
        +-- risk_report()              сводка рисков    таблица: подозрительные операции
        |
        +-- to_text(report) / export_to_text(report, path)
        +-- export_to_json(report, path)    весь отчёт, деньги строкой
        +-- export_to_csv(report, path)     главная таблица отчёта
        +-- save_charts(directory, client_id=None)  -> [пути к PNG]
```

Отчёт — это `Report`: вид, заголовок, время, `summary` (ключ: значение)
и `tables` (имя: список строк). JSON содержит всё, CSV — одну главную таблицу.

```
   CSV          UTF-8 с BOM, разделитель ";" - русский Excel открывает по колонкам;
                текст, начинающийся с = + - @, экранируется апострофом,
                чтобы Excel не выполнил его как формулу (числа не трогаются)
   время        во всех форматах с секундами
   запись       весь текст собирается и кодируется до записи файла:
                при ошибке - InvalidOperationError, прежний файл цел
```

Графики:

```
   файл                            форма                        что показывает
   ------------------------------------------------------------------------------------
   bank_balance_by_currency.png    круговая                     доля валют в балансе, RUB
   bank_top_clients.png            горизонтальные столбцы       топ-10 клиентов по балансу, RUB
   bank_transactions_by_type.png   составные столбцы            исполнено / отклонено по типам
   risk_levels.png                 круговая                     оценки low / medium / high
   risk_rules.png                  горизонтальные столбцы       сколько раз сработало правило
   client_<id>_balance.png         ступенчатые линии            движение баланса счетов, RUB
```

Правила оформления:

```
   цвета        проверенная палитра (валидатор dataviz), слоты в фиксированном порядке;
                уровни риска - статусные цвета, у каждой доли подпись в легенде
   одна ось Y   счета в разных валютах переводятся в RUB, второй оси нет
   круговая     процент на доле только от 5%, у всех - в легенде;
                отрицательную долю нарисовать нельзя - она названа в заголовке
   столбцы      не толще 24 px, растут от нуля, значение на конце столбца;
                клиентов не больше 10, в заголовке "топ-10 из N"
   линии        легенда под графиком; подпись конца только у одиночной линии;
                одна точка во времени - ось +-1 час
   без данных   график всё равно создаётся, с надписью "Нет данных"
```

Рисование идёт через `matplotlib.figure.Figure` без `pyplot`: нет глобального
списка фигур и окон, а стиль включается через `rc_context` только на время
рисования.

Движение баланса берётся из журнала аудита: `account_opened` хранит начальный
остаток (время по часам банка), а итог исполненной операции — остатки
затронутых счетов после неё. Баланс по валютам в отчёте банка считается
пересчётом каждого счёта, поэтому строки сходятся с общим балансом до копейки.
Прямые вызовы `account.deposit()` мимо процессора в историю не попадают.

## Тесты

Около 10 секунд: графики в тестах рисуются по-настоящему.

Хеширование пароля намеренно медленное, поэтому в тестах число итераций
снижается через `monkeypatch`. Отдельный тест сторожит настоящее значение:

```python
def test_hashing_cost_is_high_in_production(self, real_password_iterations):
    assert real_password_iterations >= 200_000
```

`tests/test_demo.py` запускает демо и проверяет требования дня 6: 5-10 клиентов,
10-15 счетов, 30-50 транзакций, есть отклонённые и подозрительные, топ-3,
все разделы и события в выводе и в файлах, одинаковые итоги при повторном запуске.
`tests/test_reporting.py` проверяет содержимое трёх отчётов, значения ячеек
CSV и JSON, а у графиков — нарисованное: длины столбцов, число долей,
подписи, пределы осей и надпись "Нет данных" у пустого банка.

## Логирование

Модели не печатают ничего в консоль — они сообщают о событиях через `loguru`,
а точка входа решает, куда эти события писать.

```python
logger.info("withdrawal", account_id=..., amount=..., currency=..., balance=...)
```

```
2026-09-04 14:22:12 | INFO | withdrawal | {'account_id': '49cf87ef',
    'amount': Decimal('2000.00'), 'fee': Decimal('25.00'),
    'currency': <Currency.RUB: 'rub'>, 'balance': Decimal('-825.00')}
```

Событие — это поля, а не текст: по такому логу можно искать и считать.

Жизненный цикл транзакции:

```
   queue.add()          transaction_queued      INFO
   queue.cancel()       transaction_cancelled   INFO
   processor успех      transaction_completed   INFO
   processor отказ      transaction_rejected    WARNING, с именем ошибки
```

`configure_logging()` из `src/logging_setup.py` вызывается только в `main.py`:
основной вывод получает только события из `events`, `log_file` — все события.
Тест `test_no_print_in_domain_models` сторожит, чтобы `print` не вернулся в модели.
